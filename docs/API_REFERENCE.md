## Public API vs Internal API

**Use these:**

- `qch.QCH` and everything reachable from a `QCH` instance
  (`hub.circuits`, `hub.versions`, `hub.provenance`, `hub.artifacts`,
  `hub.metrics`, `hub.benchmarks`, `hub.verifications`,
  `hub.evolution`, `hub.tags`, `hub.ingestion`, `hub.submissions`,
  `hub.materializations`)
- `qch.models` — the dataclasses every method above returns
- `qch.exceptions` — `QCHError` and its subclasses
- `qch.importers` — `QASMImporter`, `QASMImportResult`,
  `ECDSAFailImporter`, `ImportResult`, `ECDSAFailHistoryImporter`,
  `HistoryImportResult`, `HistoryScanResult`
- `qch.artifact_store` — `ArtifactStore`, `LocalArtifactStore`,
  `PutResult`, `ArtifactStoreError` (DB-2 Phase A6)
- `qch.materializers` — `Materializer`, `MaterializationContext`,
  `MaterializationOutput`, `MaterializationError`,
  `MaterializationTimeoutError`, and
  `qch.materializers.ecdsafail.ECDSAFailMaterializer` (DB-2 Phase A6)

**Do not depend on these directly:**

- `qch.storage` / `qch.storage.sqlite.backend.SQLiteStorage` — the
  concrete SQLite implementation. `QCH.open(...)` constructs one for
  you; you never need to import it yourself.
- `qch.repositories.interfaces.Storage` — the internal `Protocol`
  every backend implements. It exists so `services/*.py` and `QCH`
  never import `sqlite3`, not as something application code calls.
- The SQL schema (`qch/storage/sqlite/migrations/001_initial.sql`) —
  table names, column names, and constraints are an implementation
  detail of the SQLite backend and may change between schema versions
  without any change to the Python API above.

If you find yourself importing anything under `qch.storage` or
`qch.repositories` from application code, that is a sign you've
reached past the intended public surface.

## Current API Stability

**This is an early QCH API.** DB-1 (the generic core + SQLite
backend), DB-1.1 (`QASMImporter`), and DB-1.2 (multi-circuit
validation) have proven the architecture, but method names,
signatures, and default behaviors documented here may still change
before a stable release — in particular:

- Some "idempotent" methods silently keep the *first*-written row on a
  repeat call (new argument values are ignored); others actually
  *update* the existing row. This asymmetry (detailed per-method
  below) is a known rough edge, not a guaranteed-permanent contract —
  see the callout under [`MetricsService.record()`](#recordversion_id-str-metric_name-str-metric_value-float--metric_unit-str--none--none-computation_method-str--none--none-metadata-dictstr-any--none--none---structuralmetric).
- `VerificationsService.list()`'s multi-filter behavior (OR, not AND)
  and `IngestionService.list()`'s "no filter means return everything"
  default are both real, current behavior, but not designed-and-agreed
  API contracts.
- No package has been published; everything here is read directly from
  `src/qch/` in this repository.

Do not build a long-lived integration against exact wording of error
messages, or against the "first write wins vs. update" split above,
without re-checking this document against the source it was generated
from.

## `QCH`

`qch.hub.QCH` (also importable as `qch.QCH`). The single entry point —
one instance per store, exposing one service object per entity family.

### `QCH(storage: Storage, *, artifact_store: ArtifactStore | None = None, materializers: list[Materializer] | None = None, structural_parsers: list[StructuralParser] | None = None) -> QCH`

Direct constructor. Takes an already-built `Storage` implementation.
Normal code should use `QCH.open(...)` instead — this form exists for
tests and for a future non-SQLite backend. `artifact_store`/
`materializers`/`structural_parsers` are the same parameters
`QCH.open()` takes — see below.

### `QCH.open(store: str | Path, *, artifact_store: ArtifactStore | None = None, materializers: list[Materializer] | None = None, structural_parsers: list[StructuralParser] | None = None) -> QCH`

Classmethod. Opens (creating if needed) a QCH store at `store` — a
filesystem path, or `":memory:"` for a transient, process-local store.
Runs any pending schema migrations automatically. Backed by SQLite
today.

`artifact_store` (DB-2 Phase A6) is where materialized `Artifact` BYTES
live — defaults to a `LocalArtifactStore` at `"<store>.artifacts/"`
(or a disposable temp directory for `":memory:"`). `materializers`
(also A6) is the list of `Materializer` plugins `hub.materializations`
may use, and `structural_parsers` (DB-3 Phase A7) is the list of
`StructuralParser` plugins `hub.structures` may use — **both default to
`[]`**: `qch.hub` never assumes any dataset-specific plugin exists,
exactly like it never auto-wires `ECDSAFailImporter`. Pass e.g.
`materializers=[ECDSAFailMaterializer(r"...\ecdsafail-challenge")]`,
`structural_parsers=[QasmStructuralParser(), ECDSAOpsStructuralParser()]`
explicitly to enable them.

```python
hub = QCH.open("my-qch.sqlite3")
hub2 = QCH.open(":memory:")

from qch.materializers.ecdsafail import ECDSAFailMaterializer
hub3 = QCH.open("my-qch.sqlite3", materializers=[ECDSAFailMaterializer(r"C:\...\ecdsafail-challenge")])
```

### `hub.close() -> None`

Closes the underlying storage connection.

### `hub.__enter__() -> QCH` / `hub.__exit__(*exc_info) -> None`

`QCH` supports the context-manager protocol; `__exit__` calls
`close()`.

```python
with QCH.open("my-qch.sqlite3") as hub:
    ...
```

## `CircuitsService` (`hub.circuits`)

`qch.services.circuits.CircuitsService`. `LogicalCircuit` operations.

### `create(logical_circuit_id: str, name: str, *, domain: str | None = None, description: str | None = None, semantic_spec: str | None = None, metadata: dict[str, Any] | None = None) -> LogicalCircuit`

Creates a new `LogicalCircuit`.

- **Raises:** `DuplicateError` if `logical_circuit_id` already exists.
- **Idempotency:** none — a second call with the same ID always raises.
  Use `get_or_create()` if you want idempotent creation.

```python
circuit = hub.circuits.create("qch:logical:ghz_5", name="GHZ-5")
```

### `get_or_create(logical_circuit_id: str, name: str, *, domain: str | None = None, description: str | None = None, semantic_spec: str | None = None, metadata: dict[str, Any] | None = None) -> LogicalCircuit`

Returns the existing `LogicalCircuit` if `logical_circuit_id` is
already known; otherwise creates it.

- **Idempotent by construction.** Natural key: `logical_circuit_id`.
- **First write wins:** if the circuit already exists, its stored
  `name`/`domain`/`description`/`semantic_spec`/`metadata` are
  returned **unchanged** — this call's arguments for those fields are
  silently ignored on a repeat call **(verified by testing)**.

```python
circuit = hub.circuits.get_or_create("qch:logical:ghz_5", name="GHZ-5")
```

### `get(logical_circuit_id: str) -> LogicalCircuit`

- **Raises:** `NotFoundError` if no such circuit exists.

```python
circuit = hub.circuits.get("qch:logical:ghz_5")
```

### `list() -> list[LogicalCircuit]`

Every `LogicalCircuit` in the store, ordered by `logical_circuit_id`.
Takes no arguments — there is no per-circuit filter here (filter the
returned list yourself if needed).

```python
for circuit in hub.circuits.list():
    print(circuit.name)
```

## `VersionsService` (`hub.versions`)

`qch.services.versions.VersionsService`. `CircuitVersion` operations.
See [`qch.models.CircuitVersion`](#circuitversion) for the identity
rules this service preserves — `version_id` is always
backend-generated, never derived from a commit SHA, an
`external_version_key`, or a `structural_fingerprint`.

### `create(logical_circuit_id: str, *, external_version_key: str | None = None, version_label: str | None = None, sequence_no: int | None = None, historical_time: str | None = None, structural_fingerprint: str | None = None, realized_from_submission_id: str | None = None, metadata: dict[str, Any] | None = None) -> CircuitVersion`

Creates a new `CircuitVersion` of `logical_circuit_id`. `version_id` is
always generated internally.

- **Raises:** `DuplicateError` if `external_version_key` is given and
  already used by another version — the database enforces
  `external_version_key` as unique. This is **not** stated in this
  method's source (it has no docstring) and is only enforced by the
  SQLite schema one layer down; documented here **(verified by
  testing)** rather than inferred from the code you'd normally read.
- **Idempotency:** none of its own — calling it twice with the same
  `external_version_key` raises rather than returning the first
  version. Use `get_or_create()` for idempotent creation.
- `realized_from_submission_id` (added in DB-2 Phase A1) is **optional**
  and defaults to `None` — most `CircuitVersion`s have no known
  `Submission` at all. It is a plain pass-through to storage: no lookup
  or validation happens in this method itself. Prefer
  `hub.submissions.link_version(...)` if the version already exists and
  you want to link it after the fact — it also enforces the "can't
  relink to a different submission" rule (see
  [`SubmissionsService.link_version`](#link_versionsubmission_id-str-version_id-str---circuitversion)).

```python
version = hub.versions.create("qch:logical:ghz_5", version_label="v1")
```

### `get_or_create(logical_circuit_id: str, external_version_key: str, *, version_label: str | None = None, sequence_no: int | None = None, historical_time: str | None = None, structural_fingerprint: str | None = None, realized_from_submission_id: str | None = None, metadata: dict[str, Any] | None = None) -> CircuitVersion`

Looks up by `external_version_key` first; returns the existing version
if found, otherwise creates one. This is what makes
`ECDSAFailImporter`/`QASMImporter` idempotent.

- **Idempotent by construction.** Natural key: `external_version_key`
  (note: unlike `create()`, this parameter is **required** here, not
  optional).
- **First write wins:** an existing version's fields are returned
  unchanged, **including `realized_from_submission_id`** — this call's
  other arguments are ignored on a repeat call.

```python
version = hub.versions.get_or_create(
    "qch:logical:ghz_5", external_version_key="sha256:abc...", version_label="v1",
)
```

### `get(version_id: str) -> CircuitVersion`

- **Raises:** `NotFoundError` if no such version exists.

### `find_by_external_key(external_version_key: str) -> CircuitVersion | None`

Returns `None` (not an exception) if no version has that key.

### `list(logical_circuit_id: str) -> list[CircuitVersion]`

Every version of `logical_circuit_id`, in historical order (by
`sequence_no`, nulls last, then `historical_time`, then insertion
order). Never returns another circuit's versions.

```python
for version in hub.versions.list(circuit.logical_circuit_id):
    print(version.version_label)
```

### `set_status(version_id: str, record_status: str) -> CircuitVersion`

The **only** supported way to change a `CircuitVersion` after creation
— there is no generic "update everything" method (see
[DB1_ARCHITECTURE.md](DB1_ARCHITECTURE.md#immutability)).

- **Raises:** `ValidationError` if `record_status` is not one of
  `qch.models.RECORD_STATUSES` (`"ACTIVE"`, `"SUPERSEDED"`,
  `"INVALID"`, `"RETRACTED"`); `NotFoundError` if `version_id` doesn't exist.

```python
from qch.models import RECORD_STATUSES
hub.versions.set_status(version.version_id, "SUPERSEDED")
```

## `ArtifactsService` (`hub.artifacts`)

`qch.services.artifacts.ArtifactsService`. `Artifact` operations —
external circuit-representation references. Never holds artifact
bytes.

### `add(version_id: str, artifact_type: str, uri: str, *, format: str | None = None, sha256: str | None = None, size_bytes: int | None = None, status: str = "READY", metadata: dict[str, Any] | None = None) -> Artifact`

- **Idempotent by construction.** Natural key: `(version_id, uri)`.
- **First write wins:** if an artifact with that `(version_id, uri)`
  already exists, it is returned **unchanged** — a different `sha256`,

  **(verified by testing)**.

```python
artifact = hub.artifacts.add(
    version.version_id, "circuit", "ghz5.qasm", format="QASM", sha256="e9cbcca6...",
)
```

## `MetricsService` (`hub.metrics`)

`qch.services.metrics.MetricsService`. `StructuralMetric` operations —
a flexible name/value relation so new metric names never require a
schema change.

### `record(version_id: str, metric_name: str, metric_value: float, *, metric_unit: str | None = None, computation_method: str | None = None, metadata: dict[str, Any] | None = None) -> StructuralMetric`

- **Idempotent by construction.** Natural key: `(version_id, metric_name)`.
- **This one is an upsert, unlike most other `.add()`/`.create()`
  methods in this API:** calling it again with the same
  `(version_id, metric_name)` **overwrites** `metric_value`,
  `metric_unit`, `computation_method`, and `metadata` with this call's
  values **(verified by testing)** — the opposite behavior from
  `ArtifactsService.add()`, `BenchmarksService.add()`,
  `VerificationsService.add()`, and `EvolutionService.add_edge()`,
  which all keep the first-written row. See
  ["Current API Stability"](#current-api-stability).

```python
hub.metrics.record(version.version_id, "qubit_count", 5)
```

### `get(version_id: str, metric_name: str) -> StructuralMetric | None`

### `list(version_id: str) -> list[StructuralMetric]`

## `BenchmarksService` (`hub.benchmarks`)

`qch.services.benchmarks.BenchmarksService`. `BenchmarkRun`
operations — evidence *about* a version, not an intrinsic property of
it. A version may have zero, one, or many.

### `add(version_id: str, benchmark_name: str, *, benchmark_version: str | None = None, run_time: str | None = None, shots: int | None = None, toffoli_count: int | None = None, peak_qubits: int | None = None, score: int | None = None, status: str = "PENDING", environment: dict[str, Any] | None = None, result: dict[str, Any] | None = None) -> BenchmarkRun`

- **Idempotent by construction.** Natural key:

```python
run = hub.benchmarks.add(
    version.version_id, "ecdsafail:point_add", toffoli_count=1320763, peak_qubits=1152, score=1521518976,
)
```

## `VerificationsService` (`hub.verifications`)

`qch.services.verifications.VerificationsService`. `VerificationResult`
operations. Every result names **exactly one** target.

### `add(verification_type: str, status: str, *, version_id: str | None = None, artifact_id: str | None = None, benchmark_run_id: str | None = None, method: str | None = None, verifier: str | None = None, verified_at: str | None = None, details: dict[str, Any] | None = None) -> VerificationResult`

- **Raises:** `ValidationError` unless **exactly one** of
  `version_id`/`artifact_id`/`benchmark_run_id` is given (zero or more
  than one both raise) — checked here in Python, and again by a
  database `CHECK` constraint as defense in depth.
- **Idempotent by construction.** Natural key:
  `(verification_type, target)`.
- **First write wins**, same pattern as `ArtifactsService.add()`
  **(verified by testing)**.

```python
hub.verifications.add("serialization_round_trip", "PASS", artifact_id=artifact.artifact_id)
```

### `list(*, version_id: str | None = None, artifact_id: str | None = None, benchmark_run_id: str | None = None) -> list[VerificationResult]`

- If **no** filter is given, returns **every** `VerificationResult` in
  the entire store **(verified by testing)** — not an empty list.
- If **more than one** filter is given, they are combined with **OR**,
  not AND **(verified by testing, from reading the SQLite backend)**:
  `list(artifact_id=a, benchmark_run_id=b)` returns rows matching
  *either* `a` or `b`. Because a `VerificationResult` row can only ever
  have one of the three target columns set (see `add()` above), this
  behaves like a simple union of two independent lookups rather than a
  true filter intersection — but it is worth knowing explicitly before
  relying on it.

```python
hub.verifications.list(artifact_id=artifact.artifact_id)
hub.verifications.list(benchmark_run_id=run.benchmark_run_id)
```

## `EvolutionService` (`hub.evolution`)

`qch.services.evolution.EvolutionService`. The (possibly branching)
version-evolution graph.

### `add_edge(source_version_id: str, target_version_id: str, relation_type: str = "historical_successor", *, transformation_name: str | None = None, description: str | None = None, confidence: float | None = None, evidence: dict[str, Any] | None = None) -> TransformationEdge`

Note `relation_type` is positional-or-keyword with a default (it comes
*before* the `*`), unlike every other parameter here.

- **Idempotent by construction.** Natural key:
  `(source_version_id, target_version_id, relation_type)`.
- **First write wins**, same pattern as `ArtifactsService.add()`
  **(verified by testing)** — a different `confidence`/`evidence` on a
  repeat call with the same key is silently ignored.

```python
hub.evolution.add_edge(v1.version_id, v2.version_id)  # relation_type defaults to "historical_successor"
```

### `list_edges(version_id: str) -> list[TransformationEdge]`

Every edge touching `version_id`, incoming and outgoing combined
(`list_edges_from(version_id) + list_edges_to(version_id)`).

### `list_edges_from(version_id: str) -> list[TransformationEdge]`

Outgoing edges only.

### `list_edges_to(version_id: str) -> list[TransformationEdge]`

Incoming edges only.

### `predecessors(version_id: str) -> list[CircuitVersion]`

The source `CircuitVersion` of every incoming edge.

```python
for p in hub.evolution.predecessors(v2.version_id):
    print(p.version_label)
```

### `successors(version_id: str) -> list[CircuitVersion]`

The target `CircuitVersion` of every outgoing edge.

## `IngestionService` (`hub.ingestion`)

`qch.services.ingestion.IngestionService`. `IngestionJob` bookkeeping
for a future, incremental importer — exists so per-commit pipeline
progress has somewhere to be recorded.

### `record(stage: str, status: str, *, source_commit_id: str | None = None, attempt_no: int = 1, started_at: str | None = None, finished_at: str | None = None, error_type: str | None = None, error_message: str | None = None, details: dict[str, Any] | None = None) -> IngestionJob`

- **Idempotent by construction.** Natural key: `(source_commit_id, stage)`.
- **This one updates the existing row** on a repeat call (like
  `MetricsService.record()`, unlike most `.add()` methods in this API)
  — `status`, `attempt_no`, `started_at`, `finished_at`, `error_type`,
  `error_message`, and `details` are all overwritten with this call's
  values. Documented in the method's own docstring as "e.g. a retry".

```python
hub.ingestion.record("metadata_import", "SUCCESS", source_commit_id=commit.source_commit_id)
```

### `list(source_commit_id: str | None = None) -> list[IngestionJob]`

If `source_commit_id` is omitted (`None`), returns **every**
`IngestionJob` in the store **(verified by testing)**.

## `SubmissionsService` (`hub.submissions`)

`qch.services.submissions.SubmissionsService`. Added in **DB-2 Phase
A1** (see [DB2_SCHEMA_GAP_ANALYSIS.md](DB2_SCHEMA_GAP_ANALYSIS.md)).
`Submission` operations, and the role-tagged `Submission <-> SourceCommit`
relationship.

A `Submission` represents an external act of proposing work (e.g. one
ECDSA.Fail pull request / submission branch) — it is deliberately
**separate** from `SourceCommit`: one `Submission` may correspond to
**several** `SourceCommit`s playing different roles over its lifetime
(a `submitted` branch-tip commit that is later re-authored into a
different `promoted` commit on `main`), and one `SourceCommit` may play
**several roles** for the same `Submission` at once (a fast-forward
merge where the same commit is both `validated` and `promoted`). This
is why the relationship is its own table
(`submission_source_commit`, exposed as `SubmissionSourceCommit`),
never a scalar column on either side. `CircuitVersion` has an entirely
separate, optional link to at most one `Submission`
(`realized_from_submission_id`) — see
[`qch.models.CircuitVersion`](#circuitversion) and
[`qch.models.Submission`](#submission) below.

### `create(source_system: str, *, external_submission_key: str | None = None, submitted_at: str | None = None, status: str = "SUBMITTED", metadata: dict[str, Any] | None = None) -> Submission`

- **Raises:** `DuplicateError` if `external_submission_key` is given
  and already used by another submission; `ValidationError` if
  `status` is not one of `qch.models.SUBMISSION_STATUSES`.
- **Idempotency:** none of its own — calling it twice with the same
  `external_submission_key` raises. Use `get_or_create()` for
  idempotent creation.

```python
submission = hub.submissions.create("ecdsafail", external_submission_key="ecdsafail:39e28ee8-...")
```

### `get_or_create(external_submission_key: str, *, source_system: str, submitted_at: str | None = None, status: str = "SUBMITTED", metadata: dict[str, Any] | None = None) -> Submission`

Looks up by `external_submission_key` first; returns the existing
submission if found, otherwise creates one. This is what makes
`ECDSAFailImporter`'s V1–V5 submission backfill idempotent.

- **Idempotent by construction.** Natural key: `external_submission_key`.
- **First write wins**, the same pattern as
  `CircuitsService.get_or_create()`: an existing submission's
  `source_system`/`status`/`metadata` are returned **unchanged** — this
  call's other arguments are silently ignored on a repeat call.

```python
submission = hub.submissions.get_or_create("ecdsafail:39e28ee8-...", source_system="ecdsafail")
```

### `get(submission_id: str) -> Submission`

- **Raises:** `NotFoundError` if no such submission exists.

### `find_by_external_key(external_submission_key: str) -> Submission | None`

Returns `None` (not an exception) if no submission has that key.

### `list(*, status: str | None = None, source_system: str | None = None) -> list[Submission]`

If both filters are given, they are combined with **AND** (unlike
`VerificationsService.list()`'s OR-combined filters above) — this is a
true filter intersection because a `Submission` has exactly one
`source_system` and one `status` at a time, not one of several
mutually-exclusive target columns.

### `set_status(submission_id: str, status: str) -> Submission`

- **Raises:** `ValidationError` if `status` is not one of
  `qch.models.SUBMISSION_STATUSES` (`"SUBMITTED"`, `"VALIDATED"`,
  `"PROMOTED"`, `"REJECTED"`, `"ABANDONED"`); `NotFoundError` if
  `submission_id` doesn't exist.

### `link_source_commit(submission_id: str, source_commit_id: str, role: str) -> None`

Records that `source_commit_id` played `role` for `submission_id`.

- **Raises:** `ValidationError` if `role` is not one of
  `qch.models.SUBMISSION_SOURCE_COMMIT_ROLES` (`"submitted"`,
  `"validated"`, `"promoted"`).
- **Idempotent by construction.** Natural key:
  `(submission_id, source_commit_id, role)` — calling this again with
  the exact same triple is a no-op; it does **not** raise
  `DuplicateError`. The same `(submission_id, source_commit_id)` pair
  under a **different** `role` is a **separate** row, by design (see
  the Validate-era example above).

```python
hub.submissions.link_source_commit(submission.submission_id, commit.source_commit_id, "promoted")
```

### `list_source_commit_links(submission_id: str) -> list[SubmissionSourceCommit]`

Every role-tagged relationship row for `submission_id` — if the same
commit plays two roles, this returns **two** rows for it (contrast with
`list_source_commits()` below).

### `list_source_commits(submission_id: str, *, role: str | None = None) -> list[SourceCommit]`

The **distinct** `SourceCommit`s linked to `submission_id`, optionally
filtered to one `role`. A commit that plays two roles for the same
submission appears **once** here, not twice — deduplicated by
`source_commit_id`, unlike `list_source_commit_links()`.

### `find_for_source_commit(source_commit_id: str) -> list[Submission]`

Every `Submission` that has ever linked `source_commit_id`, in any
role. Ordinarily this returns a list of length 0 or 1 (one commit
usually belongs to one submission's history), but the return type is a
list because nothing in the schema prevents the same commit from being
cited by more than one submission.

### `link_version(submission_id: str, version_id: str) -> CircuitVersion`

Sets `version_id`'s `realized_from_submission_id` to `submission_id`
and returns the updated `CircuitVersion`.

- **Idempotent for the same submission:** calling this again with the
  same `(submission_id, version_id)` pair is a no-op that returns the
  version unchanged.
- **Raises:** `ValidationError` if `version_id` already has a
  **different** `realized_from_submission_id` — relinking a version to
  a different submission is refused rather than silently overwritten,
  preserving the immutability rule from
  [DB1_ARCHITECTURE.md](DB1_ARCHITECTURE.md#immutability). `NotFoundError`
  if `version_id` doesn't exist.

```python
hub.submissions.link_version(submission.submission_id, version.version_id)
```

## `QASMImporter`

`qch.importers.qasm.QASMImporter`, importable as `qch.importers.QASMImporter`.
Imports one flat OpenQASM 2 file as one `CircuitVersion`. Nothing in
this class is specific to any one circuit or dataset.

### `QASMImporter(hub: QCH) -> QASMImporter`

### `import_file(qasm_path: str | Path, *, name: str, logical_circuit_id: str | None = None, domain: str | None = None, description: str | None = None, external_version_key: str | None = None, version_label: str | None = None) -> QASMImportResult`

Parses `qasm_path` (see the supported OpenQASM 2 subset below), then
calls, in order: `hub.circuits.get_or_create(...)`,
`hub.versions.get_or_create(...)`, `hub.artifacts.add(...)`, and
`hub.metrics.record(...)` once for `qubit_count`, once for
`operation_count`, and once per distinct gate/instruction keyword seen
(as `"<keyword>_count"`).

- `logical_circuit_id` defaults to a slug of `name` if omitted, e.g.
  `"GHZ-5"` → `"qch:logical:ghz_5"`.
- `external_version_key` defaults to `"sha256:<file hash>"` if
  omitted — this is what makes `import_file()` idempotent for the
  *same file content*; see the docstring in `qasm.py` for why this is
  a narrow, documented choice for this simple importer, not a general
  QCH principle (two historical versions may share identical QASM
  content and still be distinct realizations in a more sophisticated
  importer).
- Never creates a `BenchmarkRun`, `VerificationResult`, or
  `TransformationEdge` — there is nothing to benchmark, verify, or
  link from a bare QASM file alone.
- **Idempotency:** calling `import_file()` again with the same file
  (or the same explicit `external_version_key`) returns the same
  `logical_circuit_id`/`version_id`/`artifact_id` — no duplicate rows
  are created (every underlying call is one of the "first write wins"
  idempotent methods above).

**Supported OpenQASM 2 subset** (see `qch/importers/qasm_parsing.py`):
a version pragma, one `include`, `qreg`/`creg` declarations, an
`opaque NAME(...) qargs;` declaration, a `gate NAME ... { body }`
compound definition (recognized generically and skipped as a
declaration — its body is never decomposed or counted; a later *call*
to that gate is counted as one ordinary operation named after the
gate), and a flat sequence of gate applications, `barrier` statements,
and `measure` statements. **Not** supported: classical control (`if`),
loops, OpenQASM 3.

```python
from qch.importers import QASMImporter

result = QASMImporter(hub).import_file(
    "data/mqtbench/raw/ghz_5.qasm", name="GHZ-5", domain="quantum-circuit-demo",
)
```

| Field | Type |
|---|---|
| `logical_circuit_id` | `str` |
| `version_id` | `str` |
| `artifact_id` | `str` |

## `ECDSAFailImporter`

`qch.importers.ecdsafail.ECDSAFailImporter`, importable as
`qch.importers.ECDSAFailImporter`. Imports the frozen ECDSA.Fail
`manifest.json` (V1–V5). Reads only that small, already-validated
manifest — never a `.kmx` artifact.

### `ECDSAFailImporter(hub: QCH) -> ECDSAFailImporter`

### `import_manifest(manifest_path: str | Path) -> ImportResult`

For the one `LogicalCircuit` and each of its versions in the manifest,
calls (in order) `hub.circuits.get_or_create`,
`hub.versions.get_or_create`, `hub.provenance.get_or_create_commit` +
`link_version`, `hub.ingestion.record`, `hub.artifacts.add`,
`hub.metrics.record` (once per manifest metric), `hub.benchmarks.add`,
`hub.verifications.add` (twice: `serialization_round_trip` against the
artifact, `benchmark_correctness` against the benchmark run), and,
**for V1–V5 only** (see below), `hub.submissions.get_or_create` +
`link_source_commit` + `set_status` + `link_version`, before finally
`hub.tags.add(..., "milestone")`. Finally calls
`hub.evolution.add_edge` once per manifest `transformation_edges`
entry.

**Submission backfill (DB-2 Phase A1):** the manifest itself carries no
submission identifier, so a small, module-level
`_SUBMISSION_PROVENANCE` dict in `ecdsafail.py` (keyed by the
manifest's own `version_id`) supplies the five UUIDs and role
structure researched directly from the `ecdsafail-challenge` Git
history (see
[ECDSA_DB2_HISTORY_ANALYSIS.md](ECDSA_DB2_HISTORY_ANALYSIS.md)). This
is deliberately asymmetric, not a bug:

- **V1–V3:** their own submission branches no longer exist in the
  repository, so only the `"promoted"` role is recorded, against the
  manifest's own `source_commit`. No `"submitted"` commit is invented.
- **V4:** its branch survives with a distinct tip commit — both
  `"submitted"` (the branch tip) and `"promoted"` (`main`'s re-authored
  squash commit, the manifest's `source_commit`) are recorded, as two
  **different** `SourceCommit` rows under one `Submission`.
- **V5:** its branch survives too, but its tip and `main`'s commit are
  the **same** commit object (a fast-forward, not a squash) — one
  `SourceCommit` row is linked under **both** `"validated"` and
  `"promoted"`.

Every backfilled `Submission` ends with `status = "PROMOTED"` (all five
are known, historically-completed acceptances) and is linked to its
`CircuitVersion` via `hub.submissions.link_version(...)`. If a future,
larger manifest includes a version with no entry in
`_SUBMISSION_PROVENANCE`, the importer silently skips the submission
step for it — `realized_from_submission_id` staying `None` is a normal,
supported state, not an error.

**Verification mapping** (see
[DB1_ARCHITECTURE.md](DB1_ARCHITECTURE.md)): the manifest's literal
string `"passed"` maps to `VerificationResult.status = "PASS"`;
anything else maps to `"FAIL"` for `serialization_round_trip` or
`"NOT_RUN"` for `benchmark_correctness` — a passing round-trip is
never read as, or upgraded into, benchmark correctness.

- **Idempotency:** every write above uses a natural-key method, so
  calling `import_manifest()` again with the same manifest creates no
  duplicate circuits, versions, commits, artifacts, metrics, benchmark
  runs, verifications, submissions, submission-source-commit links,
  tags, or edges **(verified by testing, including two full runs
  against the real frozen manifest)**.
- Internal helper methods (`_import_provenance`,
  `_import_artifact_and_metrics`, `_import_benchmark`,
  `_import_verifications`, `_import_submission`) are private
  implementation details, not part of the public surface.

```python
from qch.importers import ECDSAFailImporter

result = ECDSAFailImporter(hub).import_manifest("manifest.json")
```

| `version_ids` | `list[str]` | one per imported version |
| `edge_ids` | `list[str]` | one per imported `historical_successor` edge |

## `ECDSAFailHistoryImporter`

`qch.importers.ecdsafail_history.ECDSAFailHistoryImporter`, importable
as `qch.importers.ECDSAFailHistoryImporter`. Added in **DB-2 Phase A2**
— see [DB2_A2_METADATA_INGESTION.md](DB2_A2_METADATA_INGESTION.md) for
the full architecture, empirical Git-history findings, and
classification algorithm. Ingests the **complete** ECDSA.Fail Git
repository (thousands of commits, hundreds of submission branches) as
lightweight provenance metadata only — a fundamentally different scale
and purpose from `ECDSAFailImporter` above, which remains the importer
for the small, frozen, five-milestone `manifest.json` and is untouched

### `ECDSAFailHistoryImporter(hub: QCH, *, logical_circuit_id: str = "qch:logical:secp256k1_point_add", logical_circuit_name: str = "secp256k1_point_add") -> ECDSAFailHistoryImporter`

### `scan(repo_path: str | Path, *, repository: str | None = None, main_ref: str | None = None) -> HistoryScanResult`

Pure discovery — reads the Git repository via `git_adapter.GitRepo`
(read-only; never checks out, resets, or otherwise mutates it) and
classifies every submission UUID found, but performs **no QCH writes**.
`repository` defaults to an `owner/repo` string derived from the
`origin` remote URL; `main_ref` defaults to `"main"`, falling back to
`"master"`, then `"origin/HEAD"`.

### `import_history(repo_path: str | Path, *, repository: str | None = None, main_ref: str | None = None, dry_run: bool = False) -> HistoryImportResult`

Calls `scan()` internally, then (unless `dry_run=True`) persists
through `hub.circuits` / `hub.provenance` / `hub.submissions` /
`hub.versions` / `hub.ingestion` only. `dry_run=True` returns the same
discovery-derived counts without writing any submission/commit/version
metadata (opening `hub`'s own store still happens, so a brand-new
on-disk store still gets its empty schema — use `":memory:"` for a
dry run with zero on-disk footprint).

- **Idempotency:** every write uses a natural-key `get_or_create`/link
  call — re-running against the same repository and store creates no
  duplicate `SourceCommit`, `Submission`, `submission_source_commit`,
  or `CircuitVersion` rows **(verified by testing, including two full
  runs against the real repository)**.
- **Reconciliation with V1-V5:** deliberately reuses the exact
  `external_submission_key`/`external_version_key` formats
  `ECDSAFailImporter`'s frozen data already uses, so running both
  importers (in either order) against the same store never duplicates
  V1-V5 — see DB2_A2_METADATA_INGESTION.md's "Identity rules" section.
- Creates a `CircuitVersion` for every **eligible** submission (DB-2
  Phase A4 — see `docs/DB2_A4_VALIDATED_VERSION_BACKFILL.md` and
  `docs/DB2_A3_CIRCUITVERSION_ELIGIBILITY.md`): `status = "PROMOTED"`
  (reached `main` via an `Accept`/`Validate` event) **or**
  `status = "VALIDATED"` (validated on its own submission branch but
  never promoted — the same realization evidence, confirmed
  evidentially equivalent to promotion by
  `docs/DB2_A35_ACCEPT_VALIDATE_CONFIRMATION.md`). A merely-`SUBMITTED`
  submission (no validation or promotion evidence at all) remains
  `Submission`-only metadata (`realized_from_submission_id` stays
  unset). Eligibility is computed by the internal, unit-tested,
  score-independent `_is_version_eligible()` function — not stored as
  its own field anywhere.
- Never creates an `Artifact`, `BenchmarkRun`, `VerificationResult`,
  `VersionTag`, or `TransformationEdge` — for either kind of eligible
  version.

```python
from qch import QCH
from qch.importers import ECDSAFailHistoryImporter

hub = QCH.open("my-qch.sqlite3")
result = ECDSAFailHistoryImporter(hub).import_history(
    r"C:\Users\jilu\Project\QCDB\Data\ECDSA\ecdsafail-challenge"
)
print(result.imported_submissions, result.promoted_versions_created)
```

## `MaterializationsService` (`hub.materializations`)

`qch.services.materializations.MaterializationsService`. Added in
**DB-2 Phase A6** — see
[DB2_A6_MATERIALIZATION_ENGINE_V01.md](DB2_A6_MATERIALIZATION_ENGINE_V01.md)
for the full architecture, security model, and empirical results.
Turns an existing `CircuitVersion` into a concrete `Artifact` on
demand, via a pluggable `Materializer` (see below) and an
`ArtifactStore` (bytes storage, separate from the metadata database).

### `materialize(version_id: str, *, materializer_name: str | None = None, parameters: dict[str, Any] | None = None, force: bool = False) -> MaterializationJob`

- **Idempotent by default (`force=False`):** if a `SUCCESS` job already
  exists for the exact `(version_id, materializer_name,
  materializer_version, environment_fingerprint)` identity, it is
  returned unchanged and no generation runs.
- **`force=True`** always performs a new attempt (a new, higher
  `attempt_no`) — identical output bytes are still deduplicated by the
  `ArtifactStore`, but the attempt itself is recorded as new evidence.
- **Never raises on a generation failure** — a failure is recorded as
  `MaterializationJob.status = "FAILED"` with `error_type`/
  `error_message` set, and the method returns that job normally. It
  *does* raise `NotFoundError` if `version_id` doesn't exist, and
  `ValidationError` if no registered materializer can handle the
  version or `materializer_name` doesn't match a registered one.
- **Never implies correctness:** `SUCCESS` means an `Artifact` was
  produced and stored — nothing about whether the circuit it
  represents is correct (see `VerificationResult`, untouched by this
  method).

```python
job = hub.materializations.materialize(version_id)
if job.status == "SUCCESS":
    artifact = next(a for a in hub.artifacts.list(version_id) if a.artifact_id == job.output_artifact_id)
```

### `retry(job_id: str) -> MaterializationJob`

Starts a brand-new attempt for a `FAILED` or `CANCELLED` job, using
that job's own materializer and parameters. Raises `ValidationError`
for any other status (including `SUCCESS`) — you cannot "retry" a job
that didn't fail. The original job row is never modified.

### `get(job_id: str) -> MaterializationJob`

Raises `NotFoundError` if `job_id` doesn't exist.

### `list(version_id: str) -> list[MaterializationJob]`

Every attempt (any status) for this version, in creation order.

## `ArtifactStore` (`qch.artifact_store`)

Added in **DB-2 Phase A6**. The bytes-storage abstraction, deliberately
separate from the metadata `Storage` protocol — `Artifact` rows never
hold bytes, only a URI/SHA-256/size/format (unchanged since DB-1).

### `LocalArtifactStore(root: str | Path)`

The only implementation shipped in V0.1. Content-addressed:
`<root>/<sha256[:2]>/<sha256[2:4]>/<sha256>`.

- `put(source_path) -> PutResult` — streams the file in 1 MiB chunks
  (never loads a whole artifact into memory), hashes it incrementally,
  and atomically places it (`os.replace()` from a private staging
  file). Identical content is deduplicated (`PutResult.deduplicated =
  True`); no second physical copy is ever written.
- `exists(content_id) -> bool`
- `open(content_id) -> BinaryIO` — raises `ArtifactStoreError` if not present.
- `verify(content_id) -> bool` — recomputes the stored object's SHA-256
  and compares it to `content_id`; an integrity check only, never a
  correctness check of what the bytes represent.
- `delete(content_id)` — removes one physical object. No garbage
  collection is implemented in V0.1; callers are responsible for
  confirming nothing still references it.
- `path_for(content_id) -> Path` — `LocalArtifactStore`-specific
  (not part of the generic interface a cloud backend would implement).

`uri_for(content_id)` / `content_id_from_uri(uri)` — module-level
helpers converting between a content id and the
`"local-artifact-store://<content_id>"` URI form persisted on
`Artifact.uri`. A `LocalArtifactStore`'s filesystem path is **never**
persisted directly.

## `Materializer` (`qch.materializers`)

Added in **DB-2 Phase A6**. The plugin interface dataset-specific
materialization logic implements — `qch.hub`/`qch.services` depend
only on this Protocol, never on a concrete plugin.

```python
class Materializer(Protocol):
    name: str
    version: str
    def can_materialize(self, context: MaterializationContext) -> bool: ...
    def environment_fingerprint(self, context: MaterializationContext) -> str: ...
    def materialize(self, context: MaterializationContext) -> MaterializationOutput: ...
```

A `Materializer` only ever generates bytes and describes them — it
never creates a database row itself (`MaterializationsService` owns
that). `environment_fingerprint()` must be cheap and deterministic
(never a random value) since it is called before any generation work,
to check for a reusable prior `SUCCESS`.

| `format` | `str \| None` |

### `MaterializationError(RuntimeError)` / `MaterializationTimeoutError(MaterializationError)`

## `StructuralAnalysisService` (`hub.structures`)

`qch.services.structures.StructuralAnalysisService`. Added in **DB-3
Phase A7** — see
[DB3_A7_CANONICAL_STRUCTURAL_IDENTITY_V01.md](DB3_A7_CANONICAL_STRUCTURAL_IDENTITY_V01.md)
for the full canonicalization specification. Computes QCH's third
identity layer — structural identity — from an already-stored
`Artifact`'s bytes, via a registered `StructuralParser`. **Never
executes third-party code and never calls `hub.materializations`** —
this service only reads bytes that already exist.

### `analyze(version_id: str, *, artifact_id: str | None = None) -> StructuralAnalysisResult`

Selects the first artifact of the version (or the explicitly named
one) whose `format` a registered `StructuralParser` recognizes, parses
it into a `CanonicalCircuit`, computes its `structural_fingerprint`,
records that on the `CircuitVersion`, and persists
`structural.qubit_count`/`structural.classical_bit_count`/
`structural.operation_count` via the existing `hub.metrics`.

- **Idempotent:** re-analyzing the same (or a structurally identical)
  artifact under the same canonical schema version reproduces the same
  fingerprint; re-recording it is a no-op. No `force` parameter —
  analysis is a pure, cheap function of already-stored bytes, unlike
  `MaterializationsService.materialize()`.
- **Raises:** `NotFoundError` if `version_id` (or an explicit
  `artifact_id`) doesn't exist; `ValidationError` if no registered
  parser can handle any artifact of the version, or if analysis
  produces a fingerprint conflicting with one already recorded for
  this version from different content.

```python
result = hub.structures.analyze(version_id)
print(result.structural_fingerprint, result.gate_counts)
```

### `same_structure(version_id_a: str, version_id_b: str) -> bool`

Compares already-recorded `structural_fingerprint`s only — never
triggers analysis. Returns `False` if either version has not been
analyzed yet (unknown is not evidence of "different"). Raises
`NotFoundError` if either version doesn't exist.

### Exact structural search (DB-3 Phase A9.1)

Three pure-read methods over already-recorded `structural_fingerprint`
values — see
[DB3_A91_EXACT_STRUCTURAL_SEARCH.md](DB3_A91_EXACT_STRUCTURAL_SEARCH.md)
for the full design. **None of them parse, canonicalize, materialize,
or execute third-party code, and none of them call `analyze()`** — they
only ever compare fingerprint strings QCH has already computed.

#### `find_by_fingerprint(structural_fingerprint: str) -> list[CircuitVersion]`

Every `CircuitVersion` whose `structural_fingerprint` exactly equals
the given string (a plain, case-sensitive comparison of the *complete*
namespaced string, e.g. `"qch-structural-fingerprint/v1:sha256:..."` —
never a stripped-prefix match). Uses the existing
`idx_circuit_version_fingerprint` index (present since migration 001).
Returns `[]` if none match.

```python
matches = hub.structures.find_by_fingerprint(result.structural_fingerprint)
for v in matches:
    print(v.version_id)
```

#### `find_identical(version_id: str) -> list[CircuitVersion]`

Every *other* `CircuitVersion` sharing `version_id`'s own
`structural_fingerprint` — `version_id` itself is always excluded.
Returns `[]` (never raises, never triggers `analyze()`) if `version_id`
has no recorded fingerprint yet. Raises `NotFoundError` if `version_id`
itself doesn't exist.

```python
duplicates = hub.structures.find_identical(version_id)
print(f"{len(duplicates)} other version(s) share this structure")
```

#### `find_duplicate_groups() -> list[StructuralDuplicateGroup]`

Every `structural_fingerprint` currently shared by 2+ **distinct**
`CircuitVersion`s, each paired with all versions sharing it. Never
returns a singleton or `NULL`-fingerprint group, and never merges or
deduplicates the underlying `CircuitVersion` rows — they remain
historically distinct. Deterministically ordered by fingerprint string.

```python
for group in hub.structures.find_duplicate_groups():
    print(group.structural_fingerprint, [v.version_id for v in group.versions])
```

#### `StructuralDuplicateGroup` (dataclass)

| Field | Type |
|---|---|
| `structural_fingerprint` | `str` |
| `versions` | `list[CircuitVersion]` |

## Canonical circuit representation (`qch.canonical`)

Added in **DB-3 Phase A7**. Generic, format-independent — see
[DB3_A7_CANONICAL_STRUCTURAL_IDENTITY_V01.md](DB3_A7_CANONICAL_STRUCTURAL_IDENTITY_V01.md)
for the complete, reproducible specification.

- `CanonicalCircuit(qubit_count, classical_bit_count, operations)` /
  `CanonicalOperation(index, name, qubits, classical_bits, parameters)`
  — both frozen dataclasses.
- `CANONICAL_SCHEMA_VERSION` (`"qch-canonical-circuit/v1"`),
  `FINGERPRINT_ALGORITHM` (`"qch-structural-fingerprint/v1"`).
- `serialize_canonical(circuit) -> bytes` — deterministic, array-based
  JSON (never pickle).
- `compute_fingerprint(circuit) -> str` —
  `"<FINGERPRINT_ALGORITHM>:sha256:<hex>"`.
- `StructuralParser` (Protocol) — `format`, `can_parse(artifact_format)`,
  `parse(content) -> CanonicalCircuit`.
- `qch.canonical.qasm_adapter.QasmStructuralParser` (`format = "qasm2"`)
  — OpenQASM 2, the same supported subset as `qch.importers.qasm_parsing`
  but extracting full operand detail.
- `qch.canonical.ecdsafail_ops.ECDSAOpsStructuralParser` (`format =
  "ops_bin"`) — the zstd-framed `"QECCOPSZ"` ECDSA.Fail wire format;
  requires the optional `zstandard` package (lazily imported).

## Exceptions (`qch.exceptions`)

All importable from `qch` directly (e.g. `from qch import NotFoundError`).

### `QCHError`

Base class for all QCH domain errors. Catch this to catch anything QCH
itself might raise.

### `NotFoundError(QCHError)`

Raised when a requested entity does not exist. Raised by:
`CircuitsService.get()`, `VersionsService.get()`,
`VersionsService.set_status()` (if the version doesn't exist),
`SubmissionsService.get()`, `SubmissionsService.set_status()`,
`SubmissionsService.link_version()` (if the version doesn't exist),
`MaterializationsService.materialize()` (if `version_id` doesn't
exist), `MaterializationsService.get()`/`.retry()` (unknown `job_id`),
`StructuralAnalysisService.analyze()`/`.same_structure()` (unknown
`version_id` or explicit `artifact_id`).

### `DuplicateError(QCHError)`

Raised when an operation would create a duplicate of an entity
expected to be unique. Raised by: `CircuitsService.create()` (existing
`logical_circuit_id`), `VersionsService.create()` (existing
`external_version_key` — see that method's entry above),
`SubmissionsService.create()` (existing `external_submission_key`),
and any lower-level `Storage` call that hits a `UNIQUE`/`PRIMARY KEY`
constraint the service layer didn't already guard against.

### `ValidationError(QCHError)`

Raised when caller-supplied data violates a domain rule. Raised by:
`VersionsService.set_status()` (unknown `record_status`),
`VerificationsService.add()` (zero or more than one target given),
`SubmissionsService.create()`/`set_status()` (unknown `status`),
`SubmissionsService.link_source_commit()` (unknown `role`),
`SubmissionsService.link_version()` (version already realized from a
different submission), `MaterializationsService.materialize()` (no
materializer can handle the version, or an unknown `materializer_name`
was given), `MaterializationsService.retry()` (job is not `FAILED`/
`CANCELLED`), `StructuralAnalysisService.analyze()` (no registered
`StructuralParser` can handle any artifact of the version, or the
computed fingerprint conflicts with a different one already recorded).

### `StorageError(QCHError)`

Raised for backend failures that are not one of the more specific
errors above (e.g. an unexpected constraint violation). Wraps the
original backend exception as `__cause__`. You should not normally
need to catch this specifically.
