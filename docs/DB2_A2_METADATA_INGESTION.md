# DB-2 Phase A2: full ECDSA.Fail metadata ingestion

This document describes `ECDSAFailHistoryImporter`
(`src/qch/importers/ecdsafail_history.py`) and its Git discovery
helper `GitRepo` (`src/qch/importers/git_adapter.py`) -- the DB-2
Phase A2 addition on top of DB-1 ([DB1_ARCHITECTURE.md](DB1_ARCHITECTURE.md))
and DB-2 Phase A1's `Submission` model (documented inline in
DB1_ARCHITECTURE.md's own "The `Submission` model" section).

**This is metadata/provenance ingestion only.** It never checks out a
commit, builds Rust code, generates a `.kmx` artifact or `ops.bin`,
computes a structural fingerprint from generated bytes, or runs a
benchmark/verification. See ["What this deliberately does not
do"](#what-this-deliberately-does-not-do) below.

All figures quoted here were measured directly against the local
`ecdsafail-challenge` clone by this phase's own work — see
[Empirical findings](#empirical-findings). The local repository, not
this document, is the source of truth for any future run; if it
changes (new commits, new submission branches), re-run
`scripts/import_ecdsa_history_db2.py --dry-run` to get current numbers
rather than trusting the ones printed here.

## Why a separate importer

`ECDSAFailImporter` (`ecdsafail.py`) reads the small, frozen, five-entry
`manifest.json` and creates a full scientific record per version
(`Artifact`, `BenchmarkRun`, `VerificationResult`) — it is unchanged by
this phase. `ECDSAFailHistoryImporter` reads the live Git repository
directly and creates only provenance/lifecycle metadata for
potentially thousands of submissions — a fundamentally different
scale and a fundamentally lighter-weight kind of record. Keeping them
as two classes means neither has to pretend to be the other; a caller
that only wants the five curated milestones never pays for, or risks
being broken by, full-history parsing logic, and vice versa.

## Architecture

```
ECDSA.Fail Git repository (local clone, read-only)
        |
        v
   GitRepo (git_adapter.py)          <-- pure Git discovery, zero QCH knowledge
        |  GitCommitInfo / GitBranchInfo
        v
   ECDSAFailHistoryImporter.scan()   <-- classification: Git facts -> QCH-shaped records
        |  HistoryScanResult (no QCH writes yet)
        v
   ECDSAFailHistoryImporter.import_history()   <-- persistence, via qch.QCH only
        |
        v
      qch.QCH  (hub.circuits / hub.provenance / hub.submissions / hub.versions / hub.ingestion)
        |
        v
      services/*.py -> Storage protocol -> SQLiteStorage -> SQLite
```

```
ECDSA.Fail Git
    |
    +-- main commits ----------------------------> SourceCommit
    |
    +-- submissions/<uuid> branches -------------> Submission
                                                       |
                                                       +--> submitted SourceCommit   (Accept-era only,
                                                       |                              distinct from promoted)
                                                       +--> validated SourceCommit   (Validate-era / validated
                                                       |                              orphans)
                                                       +--> promoted SourceCommit    (Accept or Validate event
                                                       |                              landed on main)
                                                       |
                                                       +--> CircuitVersion           (promoted submissions only,
                                                                                       at most one)
```

`GitRepo` never makes a QCH modeling decision (no idea what a
"Submission" or a "role" is) — see its own module docstring. All
classification lives in `ECDSAFailHistoryImporter`.

Recomputed directly from the local `ecdsafail-challenge` clone as part
of this phase (not copied from `ECDSA_DB2_HISTORY_ANALYSIS.md`) —
see `tests/test_qch_ecdsafail_history_real_repo.py::
test_scan_matches_freshly_computed_git_evidence`, which re-derives
these independently via raw `git` on every run and fails loudly if
they ever drift:

| Fact | Count |
|---|---|
| Commits reachable from `main` | 1,418 |
| Commits reachable from any ref | 2,005 |
| `submissions/<uuid>` branches (local + `origin/`, deduplicated) | 679 |
| Malformed `submissions/*` branch names | 0 |
| `Accept submission <uuid>` commits on `main` | 428 |
| `Validate submission <uuid>` commits on `main` | 92 |
| Merge commits on `main` (2 parents) | 4 |
| Unique submission UUIDs (branch ∪ main-event) | 1,003 |

These match exactly what `ECDSA_DB2_HISTORY_ANALYSIS.md` reported for
`main`/branch totals — this snapshot has not changed since that
research. No discrepancy to report.

### The five-way submission partition

Every one of the 1,003 unique UUIDs falls into exactly one of these
(mutually exclusive, exhaustive) categories:

| Category | Count | Evidence |
|---|---|---|
| Accept-era promoted, branch survives | 104 | branch tip = plain `Submission <uuid>`; a *different* `Accept submission <uuid>` commit is on `main` |
| Accept-era promoted, branch deleted | 324 | only the `Accept submission <uuid>` commit on `main` is known (matches V1-V3) |
| Validate-era promoted (fast-forward) | 92 | branch tip = `Validate submission <uuid>`, and that exact commit is on `main` (matches V5) |
| Validated but never promoted | 261 | branch tip = `Validate submission <uuid>`, but that commit is **not** reachable from `main` |
| Submitted only | 222 | branch tip = plain `Submission <uuid>`, no promotion event anywhere |

`104 + 324 + 92 + 261 + 222 = 1,003`. The middle three rows sum to
`520` promoted submissions (`428` distinct Accept UUIDs + `92`
Validate UUIDs); `261 + 222 = 483` remain metadata-only, no
`CircuitVersion`.

**Note on branch tip conventions:** every surviving submission
branch's tip commit is *either* `Submission <uuid>` (the raw
submission, 326 branches) or `Validate submission <uuid>` (353
branches) — never anything else. There is no separate, earlier
"submission" commit beneath a validate commit on these synthetic
branches; the branch's one distinguishing commit already carries
whichever status applies. This is a repository-specific convention
(the ECDSA.Fail challenge's submission bot appears to write exactly
one commit per branch), not a general QCH assumption.

| QCH entity | Count |

## Empirical commit-message patterns

Anchored, case-sensitive, taken directly from real commit subjects —
never loosened to a substring match:

```
^Accept submission ([0-9a-fA-F-]{36})$      -- on main only
^Validate submission ([0-9a-fA-F-]{36})$    -- on main, or at a branch tip
^Submission ([0-9a-fA-F-]{36})$             -- at a branch tip only
```

Branch names: `^submissions/([0-9a-fA-F-]{36})$`. Anything matching
`submissions/*` but failing that pattern is recorded in
`malformed_submission_refs` and skipped, never crashing the run (none
existed in this snapshot, but the defensive path is unit-tested with a
synthetic malformed branch).

## Classification algorithm

For every unique submission UUID (from branch names ∪ main-history
events):

1. **A promotion event exists on `main`** (`Accept` or `Validate`):
   link that commit `promoted`; if it was specifically a `Validate`
   event, also link the **same** commit `validated` (a second
   role-tagged row, not a second `SourceCommit` — see DB-2 Phase A1).
   If a surviving branch's tip is a *different* commit, link it
   `submitted` too (Accept-era, two `SourceCommit`s). Status →
   `PROMOTED`. Exactly one `CircuitVersion` is created/reused (see
   below).
2. **No promotion event, but the branch tip says `Validate submission
   <uuid>`:** link that commit `validated`. Status → `VALIDATED`. No
   `CircuitVersion` (deferred).
3. **No promotion event, plain `Submission <uuid>` tip (or an
   unrecognized tip subject, conservatively):** link that commit
   `submitted`. Status → `SUBMITTED`. No `CircuitVersion` (deferred).

Absence of promotion is never read as rejection — `REJECTED`/
`ABANDONED` are never assigned by this importer (DB-2 Phase A2 section
12); the existing `SUBMISSION_STATUSES` vocabulary from Phase A1
(`SUBMITTED`/`VALIDATED`/`PROMOTED`/`REJECTED`/`ABANDONED`) was
sufficient without any schema change.

## Identity rules (reconciliation with V1-V5, by construction)

- **`SourceCommit.commit_sha`** is always the 7-character abbreviated
  SHA (`full_sha[:7]`) — exactly the form `manifest.json` already uses
  for V1-V5. Verified collision-free across all 2,005 commits reachable
  from any ref in this repository snapshot
  (`git rev-list --all | cut -c1-7 | sort | uniq -d` → empty). If a
  future, larger snapshot ever produces a collision, the importer falls
  back to the full 40-character SHA for just the colliding commits and
  records a warning — it never silently merges two different commits
  under one row.
- **`Submission.external_submission_key`** is `"ecdsafail:<uuid>"` —
  exactly the format `ECDSAFailImporter`'s own frozen
  `_SUBMISSION_PROVENANCE` table already uses.
- **`CircuitVersion.external_version_key`** is
  `"ecdsafail:<7-char promoted SHA>"` — exactly the format
  `manifest.json`'s own `version_id` field already uses for V1-V5.
  This is deliberately the *same* namespace the frozen importer uses,
  not a new `"ecdsafail:submission:<uuid>"` one: reusing it is what
  makes `get_or_create()` find V1-V5's existing rows instead of
  creating duplicates, with zero special-casing in either importer.

Verified directly (`tests/test_qch_ecdsafail_history_real_repo.py::
test_v1_through_v5_are_unchanged_by_history_import`, plus manual
cross-order testing during development): running `ECDSAFailImporter`
then `ECDSAFailHistoryImporter`, or the reverse order, on the same
store produces identical final state — V1-V5's version IDs,
`Submission` rows, artifacts, metrics, benchmark runs, verification
results, tags, and evolution edges are all bit-for-bit the same either
way, and the *total* `Submission`/`CircuitVersion` counts (1,003 / 520)
never change based on ordering.

## Idempotency and resumability

Every write is a natural-key `get_or_create`/idempotent-link call (see
`qch.services.submissions.SubmissionsService`,
`qch.services.provenance.ProvenanceService`) — running
`import_history()` twice against the same repository and store
produces identical entity counts (proven for both a synthetic repo and
the real one). `hub.ingestion.record(stage="metadata_import", ...)` is
called once per `SourceCommit`, reusing the exact stage name
`ECDSAFailImporter` already established — its natural key is
`(source_commit_id, stage)`, so a repeat run **updates** that job's
`finished_at`/`details` rather than creating a new row (an intentional
audit-trail upsert, not a duplicate).

This importer does not implement checkpoint-based partial resume
(no `DISCOVER_SOURCE` → `IMPORT_SOURCE_METADATA` → ... stage machine):
at the current scale (~1,400 main commits, ~1,000 submissions, tens of
seconds end to end against a real SQLite file — see
[Performance](#performance)), a full re-run after an interruption is
cheap and always converges to the same state because every write is
independently idempotent. A future, much larger crawl (real DB-2 Phase
B+, walking a repository orders of magnitude bigger) is where a genuine
per-commit `IngestionJob` state machine would start to matter — the
`stage`/`status` values already used here would extend to that
directly, without a schema change.

## Performance (this snapshot, this machine)

| Measurement | Value |
|---|---|
| Git discovery (`scan()`, no QCH writes) | ~0.4s |
| Full persistence to `:memory:` | ~0.7-0.8s |
| Full persistence to a file-backed SQLite store | ~18-42s (varies by run/disk state) |
| Resulting store size (history data only) | ~1.8 MB |

The gap between `:memory:` and file-backed persistence reflects
per-write disk commit overhead in the current `SQLiteStorage` backend,
not this importer's own logic (the same ~1,100-1,200 writes happen
either way). This is a first real-scale baseline, not a target for
optimization in this phase — DB-2 Phase A2's brief explicitly excludes
performance tuning.

## What this deliberately does not do

- No `.kmx`/`ops.bin` generation, no Rust build, no commit checkout.
- No `Artifact`, `BenchmarkRun`, or `VerificationResult` rows for
  newly-discovered submissions — `structural_fingerprint` stays `NULL`.
- No `historical_successor` (or any) `TransformationEdge` for newly
  created versions. Git ancestry is provenance, not circuit evolution
  (DB-2 Phase A2 section 3), and no unambiguous ordering across ~520
  promoted, independently-authored submissions has been established --
  a naive main-commit-order chain was considered and explicitly
  rejected as invented provenance. All `519` (`520 - 1`) such edges are
  reported as deferred, not created.
- No `source_commit_parent` (multi-parent Git ancestry), no
  `submission_event`, no `provenance_source` table. The 4 merge
  commits found on `main` are stored using only the existing scalar
  `SourceCommit.parent_commit_sha` (first parent only) — their second
  parent is not represented anywhere; this is a real, reported
  limitation of the current schema, not a bug, and does not warrant a
  new migration by itself (DB-2 Phase A2 section 34).
- No CircuitVersions for the 483 non-promoted submissions. They are
  fully represented as `Submission` + `submission_source_commit`
  metadata and are queryable (`hub.submissions.list(status=...)`), but
  materializing a `CircuitVersion` for a submission QCH cannot prove
  reached any authoritative branch would be inventing history.
- No migration `003_*.sql`. Everything above fits `001_initial.sql` +
  `002_submission.sql` as they already exist.

## Limitations to carry into the next phase

- Merge-commit second parents are not recorded (see above) —
  `source_commit_parent` (P1, still deferred) would fix this properly.
- 483 submissions have no `CircuitVersion` — a future phase could
  define a principled, evidence-based rule for realizing some of them
  (e.g. validated-but-unpromoted) without materializing artifacts, but
  that rule was not obvious enough to invent here.
- No evolution graph exists yet across the ~520 promoted history
  versions (only V1→V2→...→V5's five, pre-existing, untouched edges do).
